# CIRCUITMIND AI

CIRCUITMIND AI is a local engineering workbench for turning electronics requirements and supplied inventories into traceable project data. **Implemented slices:** deterministic intake/feasibility, a versioned circuit graph with a JSON editor, graph validation and revision snapshots; a standalone C++20 core with bounded DC MNA (linear elements, piecewise-linear diode active sets, and explicit-parameter Shockley Newton solves), source sweeps, R/L/C AC frequency sweeps, RC/RLC backward-Euler simulation, and bounded combinational digital truth tables and sampled rising- or falling-edge D flip-flop waveforms; and a deterministic single-pole RC low-pass synthesis/analyze/test workflow using the native core. The Python DC MNA and generic RC transient entry points now delegate their numerical solves to C++ while retaining Python validation, graph mapping, and report formatting. Other slices include revision-bound engineering calculations, a gated KiCad XML netlist exporter, read-only symbol audits, source-hashed datasheet text intake, KiCad ERC/DRC adapters, and an ngspice batch adapter for user-imported decks when available.

The native engineering core is CPU-only and C++20. The CMake project configures no CUDA/GPU toolchain or required GPU library. Python remains responsible for HTTP/API orchestration, unit normalization, graph mapping, workflow/synthesis orchestration, and evidence formatting; numerical DC/AC/transient and digital truth-table/sampled-waveform execution use the single native C++ core through the stable C ABI.

## Run

The Python web application requires Python 3.11+ and uses the standard library. Building the native core requires CMake 3.20+ and a C++20 compiler. Build the native C++20 core for DC operating-point/source-sweep, AC sweep, RC/RLC transient, digital truth-table/waveform, and RC synthesis endpoints (the app can still start without it, but solver requests return HTTP 503 until the core is built):

```bash
cmake -S . -B build -DCIRCUITMIND_BUILD_TESTS=ON
cmake --build build --config Release
ctest --test-dir build --output-on-failure
python -m circuitmind
```

Open <http://localhost:8000>. To bind for a preview or choose another project directory:

```bash
CIRCUITMIND_HOST=0.0.0.0 CIRCUITMIND_PORT=8000 CIRCUITMIND_DATA_DIR=./workspace python -m circuitmind
```

The server is intended for local use. It does not offer a general shell, arbitrary build, or model-provider credential store; it can invoke fixed KiCad/ngspice adapters and Poppler text extraction on user-imported files when those tools are installed. Those native processes are not OS-isolated, so do not expose the app to an untrusted network or run it against untrusted input files.

## What works

- Intake accepts a natural-language project brief, a line-based component inventory, and discrete-logic or ESP32-hybrid direction.
- The benchmark feasibility check identifies insufficient stock instead of silently replacing supplied parts.
- Projects persist requirements, parsed BOM, architecture notes, assumptions/calculation examples, a validation ledger, and a ZIP export.
- The standalone C++20 core (`core/`) provides bounded dense DC MNA for linear R/V/I networks plus separate piecewise-linear active-set and explicitly parameterized Shockley Newton diode models, native pointwise DC source sweeps, linear R/L/C AC frequency sweeps, fixed-step backward-Euler RC/RLC transient solving, combinational logic truth tables, and sampled rising- or falling-edge D flip-flop waveforms behind a versioned C ABI. Python adapters marshal explicit inputs and preserve report contracts, while numerical solves run in C++; graph mapping and workflow orchestration remain Python-owned. DC operating point/source sweep supports up to 500 elements, 150 non-ground nodes, and 180 total unknowns (sweeps up to 200 points on one independent source); AC supports up to 200 elements, 64 non-ground nodes, 80 unknowns, and 200 positive-frequency points; transient supports up to 100 elements, 24 non-ground nodes, 32 unknowns, and 2,000 steps. AC uses explicit RMS source phasors and ideal, frequency-independent R/L/C models; none of these solvers is nonlinear SPICE validation. Python also provides unit-checked Ohm's law, resistor/capacitor networks, RC time constant, stored energy, a tolerance-aware E6/E12/E24 LED-resistor analysis, a clock timebase budget, and explicit-input clock-divider candidates. Project reports retain hashes; matching a hash is not engineering approval.
- GitHub Actions CI is configured for Ubuntu and Windows with Python 3.11/3.12; it builds the native C++20 core, runs CTest and the CLI self-test, and checks the Python suite plus JavaScript syntax. Local Linux checks pass; hosted matrix results remain pending.
- Circuit-model schema v2 stores component references, symbol IDs, pin metadata, placement coordinates, nets, and pin-to-net terminals.
- The UI can edit this JSON model with bounded grouped undo/redo and browser-local draft autosave/restore/discard, preview declared component-pin/net connectivity as an interactive graph-only map, ask the server for graph/schema checks, save revisions, and restore an earlier server snapshot. Browser drafts are not uploaded until the user saves a revision.
- KiCad XML netlist output is generated only when the model has components, consistent declared pins/nets, and caller-supplied symbol IDs. It is not a schematic export.
- The project UI can generate a hash-linked pin-to-net schedule as JSON and CSV from a topology-valid saved graph; it reports declared pin names and unconnected pins only, not physical wire routing, gauge, connector selection, or electrical checks.
- For saved graph-bound DC operating points, users may compare explicitly entered absolute voltage/current/power limits; for RC/RLC transient reports, they may check sampled peak capacitor voltage and inductor current. Limits are caller supplied and unverified. The check records simulation/model hashes and stale model association; limits are not sourced from or verified against part data, so this is not component qualification. The circuit editor can resolve exact symbol IDs from configured local KiCad symbol tables and compare declared pins with library metadata. Audits retain library/model SHA-256 provenance and differences; they are read-only and never fill or replace pin data.
- Datasheet PDFs can be attached by SHA-256 and optionally linked to a saved component reference. If Poppler `pdftotext` is installed, raw text extraction preserves page labels and source linkage; it does not interpret tables, verify ratings, or populate the circuit model.
- ZIP exports include revision snapshots and project artifacts; project backups can be downloaded from the library or opened project view. From the project library, a validated backup ZIP can be imported as a new project ID; the importer enforces bounded archive/member sizes, one project root, portable non-traversing paths, valid project/model JSON, topology checks, and snapshot hashes before staging files and atomically publishing the project. Imported reports and other artifacts are preserved but are not individually revalidated; no electrical analysis is performed. API: `POST /api/projects/import` with `Content-Type: application/zip` (64 MB compressed upload limit).
- Initial provider-neutral agent tooling exposes read-only `project.summary`, `circuit.validate`, and `circuit.connectivity_schedule` tools, a fixed `circuit_review` observe/execute/check workflow, and a separately gated `circuit.replace_model` proposal flow. The workflow checks project identity, saved topology, and model-hash consistency; unconnected pins are reported, not automatically treated as failures. Read-only calls are bounded to 8 per request, accept no arbitrary arguments, and are recorded with timing plus input/output hashes in a 1,000-entry SHA-256 chain; audit history omits full tool outputs. The chain detects record edits and tail truncation, but is unsigned and cannot prevent complete log rewriting. A circuit proposal validates an explicit candidate, binds it to the current model hash, expires after 30 minutes, and changes the saved model only after a separate `approve: true` request; stale and replayed proposals are rejected. Optional provider support includes an explicitly triggered model-list probe and a strict plan-only adapter for local Ollama or OpenAI-compatible endpoints, restricted to loopback HTTP. A user prompt may produce only allowlisted read-only tool calls; the plan is validated, stored with prompt/completion hashes, and shown for review before an explicit one-time execution request. The saved plan hash is checked before execution, and outputs pass deterministic identity/topology/hash checks. The planning call receives the prompt and tool policy, not saved project files; generated plans do not run automatically. After execution, an optional separate summary request can send only compact execution checks/counts to the configured local model; its narrative is labeled unverified, cites selected evidence keys, and the saved report includes the exact cited values plus a content digest. The execution report and audit link are rechecked after generation to reject evidence changed during the request. This is not an autonomous design planner and makes no electrical-value inference. The approval API is local-use only and does not authenticate a human identity.
- Initial ESP32 firmware scaffolding is available for explicitly `esp32`-architecture projects: user-supplied GPIO-to-saved-net mappings generate a hash-linked PlatformIO config and pin-mode-only C++ starter. It reports classic-ESP32 pin constraints and collisions; it does not implement application logic or claim compilation/hardware validation.
- A user can attach an existing `.kicad_sch` and request KiCad CLI schematic ERC; source replacement requires explicit confirmation and archives the previous file.
- A user can attach a restricted batch SPICE deck (`.cir`, `.sp`, `.ckt`) and request ngspice execution; confirmed replacements archive earlier decks. The static allowlist rejects control scripting and file/include directives. Integration runners retain process outputs/status and append each attempt to `tool_runs.jsonl`; simulation raw files can be downloaded.
- A user can attach an existing `.kicad_pcb` and request KiCad CLI board DRC. Upload checks only the S-expression header; confirmed replacements archive the previous board. DRC evidence and reports are retained, and zero exit alone is not called clean without explicit zero violation and unconnected-pad summaries.

Provider configuration uses `CIRCUITMIND_AGENT_PROVIDER=ollama` or `openai-compatible`, with optional `CIRCUITMIND_AGENT_BASE_URL`, `CIRCUITMIND_AGENT_MODEL`, and server-side `CIRCUITMIND_AGENT_API_KEY`. Defaults are `http://127.0.0.1:11434` for Ollama and `http://127.0.0.1:1234/v1` for OpenAI-compatible servers. Configuration is read at `GET /api/agent/providers`; `POST /api/agent/providers/probe` with `{}` explicitly probes only the configured loopback model-list endpoint. Credentials stay server-side and are never returned; capability detection does not test generation. Initial agent routes include `GET /api/agent/tools`, `GET /api/agent/workflows`, `POST /api/projects/<id>/agent/plan` with `{ "prompt":"..." }` to request a validated read-only plan from the configured local model (does not execute it), then `POST /api/projects/<id>/agent/plans/<plan_id>/execute` with `{ "execute":true }` after review to execute that plan once and run deterministic checks; optionally call `POST /api/projects/<id>/agent/executions/<execution_id>/summarize` with `{}` to request an unverified local-model narrative from the compact, hash-verified execution evidence (not the full circuit graph), `GET /api/projects/<id>/agent/executions` lists the 50 most recent reports with verified/invalid status, `GET /api/projects/<id>/agent/executions/<execution_id>` returns a report only after digest and audit-link verification, and `GET /api/projects/<id>/agent/executions/<execution_id>/summaries` rechecks saved summary digests, cited values, source-report integrity, and audit-chain links; `POST /api/projects/<id>/agent/workflows/run` with `{ "workflow":"circuit_review" }` (fixed three-step read-only review saved as a project artifact), `POST /api/projects/<id>/agent/execute` with `{ "calls": [{"tool":"circuit.validate","arguments":{}}] }` (1–8 registered read-only calls), and `GET /api/projects/<id>/agent/actions` for bounded recent audit metadata plus chain verification status. `POST /api/projects/<id>/agent/proposals` accepts `{ "tool":"circuit.replace_model", "arguments":{"model": ...} }` and only stages a topology-validated candidate; review it with `GET /api/projects/<id>/agent/proposals/<proposal_id>`, then explicitly apply it with `POST /api/projects/<id>/agent/proposals/<proposal_id>/approve` and `{ "approve": true }`. Approval is one-time, expires after 30 minutes, and is rejected if the saved graph has changed since proposal creation. This is an explicit API gate, not authenticated human identity or an AI planning loop. API routes for the model are `GET /api/projects/<id>/circuit`, `POST /api/projects/<id>/circuit/connectivity-schedule` with `{}` to save a hash-linked JSON report and CSV pin-to-net endpoint schedule (connectivity only; no physical wiring or electrical validation), `POST /api/projects/<id>/circuit/validate`, `POST /api/projects/<id>/circuit/symbols/resolve` (JSON `{ "model": ... }`), `PUT /api/projects/<id>/circuit`, `GET /api/projects/<id>/snapshots`, and `POST /api/projects/<id>/snapshots/restore` with `{"snapshot_id":"..."}`. Existing schematic operations are `PUT /api/projects/<id>/schematic` with a JSON `content` string and `POST /api/projects/<id>/integrations/kicad-erc`; PCB board operations are `PUT /api/projects/<id>/board` and `POST /api/projects/<id>/integrations/kicad-drc`. SPICE routes are `PUT /api/projects/<id>/simulation-deck` and `POST /api/projects/<id>/integrations/ngspice`. The in-process DC solver accepts a user-supplied `{ "netlist": ... }` at `POST /api/projects/<id>/simulations/dc-operating-point`; an optional `{ "type": "diode", "reference": "D1", "nodes": ["A", "K"], "forward_voltage": {"value": 0.7, "unit": "V"}, "off_resistance": {"value": 1e12, "unit": "ohm"} }` uses the native bounded piecewise-linear active-set model. Alternatively, `{ "type": "shockley_diode", "reference": "D1", "nodes": ["A", "K"], "saturation_current": {"value": 1e-12, "unit": "A"}, "ideality_factor": 1.0, "temperature_kelvin": {"value": 300, "unit": "K"} }` selects a bounded Newton model; PWL and Shockley diodes cannot be mixed in one solve. `POST /api/projects/<id>/simulations/dc-sweep` accepts `{ "netlist": ..., "sweep": { "reference": "V1", "start_value": ..., "stop_value": ..., "points": 51, "scale": "linear" } }` and varies one explicitly named independent voltage or current source; every point is a separate native C++ operating-point solve. The `/dc-sweep/from-model` route accepts `{ "mapping": ..., "sweep": ... }` and uses the saved graph only for connectivity and explicit mapped model provenance. AC analysis accepts an explicit R/L/C/independent-source AC netlist at `POST /api/projects/<id>/simulations/ac-sweep` with `{ "netlist": { "ground": "0", "frequency_sweep": { "start_frequency": ..., "stop_frequency": ..., "points": 101, "scale": "log" }, "elements": [...] }`; voltage/current sources require RMS magnitude quantities and `phase_degrees`. `POST /api/projects/<id>/simulations/ac-sweep/from-model` takes `{ "mapping": ..., "frequency_sweep": ... }`, maps connectivity from the saved graph, and requires explicit model bindings for each component or a reasoned exclusion. Both routes store full phasor traces; simulation history returns bounded final-frequency summaries plus hash integrity. The project UI supports explicit-netlist and graph-bound AC sweeps with selectable magnitude/phase traces; graph-bound execution always requires explicit model mappings. An explicit graph-bound alternative is `POST /api/projects/<id>/simulations/dc-operating-point/from-model` with `{ "mapping": { "ground_net": ..., "bindings": [...], "exclusions": [...] } }`; each saved component must be mapped to a supported R/V/I/diode type with both ordered pins and explicit typed model parameters, or explicitly excluded with a reason. No component description is parsed. `POST /api/projects/<id>/simulations/operating-limits` accepts `{ "simulation_artifact": "...", "limits": [{"reference":"R1","max_abs_voltage":{"value":...,"unit":"V"},"max_abs_current":{"value":...,"unit":"A"},"max_abs_power":{"value":...,"unit":"W"}}] }` to compare caller-supplied absolute bounds with a saved graph-bound DC operating point; hashes and stale-model status are retained, and bounds remain unverified. `POST /api/projects/<id>/simulations/transient-limits` uses the same report/limits shape for graph-bound RC/RLC traces, checking sampled capacitor-voltage or inductor-current peaks and reporting peak times; inter-sample maxima are not estimated. `POST /api/projects/<id>/simulations/transient-rc/from-model` accepts `{ "mapping": ..., "time_step": ..., "stop_time": ... }` for a graph-bound fixed-step backward-Euler RC run; capacitor initial voltages and source waveforms must be explicit. The sibling `/simulations/transient-rlc/from-model` route uses the same request shape and also accepts explicitly mapped ideal inductors with initial current; backward-Euler inductor/capacitor companion models are used in native C++. Both routes persist full voltage and reactive-state traces with hash-linked provenance; the project UI charts a selected node voltage for graph-bound RC/RLC transients, with explicit RC versus RLC selection, selectable inductor-current traces in RLC mode, and final inductor-current reporting. The UI offers an explicit-netlist DC source-sweep chart and a graph-bound DC sweep with selectable node traces; graph connectivity is reused only when the user supplies a complete explicit model mapping, and neither workflow infers electrical values. `GET /api/projects/<id>/simulations` returns bounded final-value summaries plus netlist/mapping hash integrity and whether the associated saved model changed since the run. `POST /api/projects/<id>/designs/rc-low-pass` implements a deterministic bounded single-pole synthesis using versioned explicit requirements, a global E-series R/C candidate search with explicit cutoff and preferred-resistance objectives, a schema-v2 candidate graph, cutoff/tolerance analysis, and a numerical backward-Euler test. The request requires `request_version: 1`, typed `inputs`, and an explicit `apply_to_circuit` boolean; applying the graph snapshots the prior circuit. Exclusions make a solve partial, and a complete mapping still does not establish physical/electrical correctness. Calculation routes include `POST /api/projects/<id>/calculations/led-resistor` with `{ "inputs": ..., "source_refs": ... }`, `POST /api/projects/<id>/calculations/clock-timebase` with explicit `{ "inputs": { "nominal_tick_rate": ..., "target_tick_rate": ..., "tolerance_ppm": ... } }`, `POST /api/projects/<id>/calculations/clock-divider` with explicit `{ "inputs": { "source_frequency": ..., "target_frequency": ..., "source_tolerance_ppm": ... } }`, and `GET /api/projects/<id>/calculations` for current/stale revision status. Datasheet routes are binary `PUT /api/projects/<id>/datasheets?filename=<name.pdf>&reference=<saved-ref>`, `GET /api/projects/<id>/datasheets`, and `POST /api/projects/<id>/datasheets/<sha256>/extract`. Saving a model snapshots the prior version first. Unsupported model versions fail closed; schema v1 projects are migrated to v2 without inferred symbol IDs.

## Native digital logic simulation

`POST /api/projects/<id>/simulations/digital-truth-table` accepts an explicit combinational Boolean netlist, e.g. `{ "netlist": { "inputs": ["A", "B"], "outputs": ["Y"], "gates": [{ "type": "xor", "inputs": ["A", "B"], "output": "Y" }] } }`. The C++ core computes all input rows and rejects cycles, undriven nets, and multiple drivers.

`POST /api/projects/<id>/simulations/digital-waveform` accepts an explicit sampled input sequence and gate list, e.g. `{ "netlist": { "inputs": ["D", "CLK"], "outputs": ["Q"], "gates": [{ "type": "dff", "inputs": ["D", "CLK"], "output": "Q", "initial_value": 0 }], "samples": [{"D": 0, "CLK": 0}, {"D": 1, "CLK": 1}], "sample_interval_s": 0.001 } }`. Input frames are in sample order and each must specify every primary input as integer 0 or 1. DFFs capture D on their selected sampled clock edge (rising by default), begin with the explicit `initial_value`, and expose Q after capture; each clock is assumed low before sample zero. The C++ core evaluates combinational gates around registered state and returns per-sample output traces; reports and bounded summaries are persisted with input/model hashes. The project view exposes explicit-netlist AC magnitude/phase sweeps through selectable node charts, combinational verification through a truth-table dialog with a half-adder example, and sequential verification through a digital-waveform dialog with an editable JSON netlist, a two-bit counter starter example, an output chart, and a bounded sample table.

Limits: truth tables support 10 inputs; sampled waveforms support 32 inputs and 10,000 samples; both support 32 outputs, 512 gates, and 256 nets. This is ideal zero-delay Boolean simulation with sample-triggered rising- or falling-edge D flip-flops—not a general HDL/discrete-event simulator. Propagation delays, setup/hold, metastability, analog thresholds, electrical loading, timing closure, and analog/digital co-simulation are not modeled.

## ESP32 firmware scaffold (initial slice)

For a project created with `architecture: "esp32"`, `POST /api/projects/<id>/firmware/scaffold` accepts `{ "target": "esp32dev", "pins": [{ "signal": "display_data", "gpio": 23, "direction": "output", "net": "DISPLAY_DATA" }] }`. The named net must exist in the validated saved graph; signal names and GPIO assignments must be unique. The response names hash-linked manifest, `main.cpp`, and `platformio.ini` artifacts plus an extractable project ZIP with the expected PlatformIO `src/main.cpp` layout; artifacts are retrievable through the project artifact endpoint and included in the project ZIP. The generated source only sets pin modes and contains a behavior TODO. Compilation remains `not-run`; exact board/module identity, peripherals, circuit voltage/current compatibility, application behavior, and hardware safety are not verified. Classic ESP32 restrictions are enforced where known, and boot-strapping/UART0 overlaps are warned. This is not generated for discrete-only projects.

## Engineering limits (important)

Graph validation checks references, pin existence, duplicate assignments, and model structure only. It does **not** establish electrical correctness, datasheet provenance, symbol-library validity, ERC/DRC, or a physically drawable/editable KiCad schematic. The XML netlist candidate is not run through KiCad here because `kicad-cli` is not installed; the symbol audit has only been exercised against controlled test libraries, not this environment's installed libraries. The ERC and ngspice adapters invoke trusted local CLIs with timeouts and no shell, but **are not OS/container sandboxes**, so only import files/decks you trust. Their binaries are not installed in this environment; no KiCad ERC or ngspice run was performed here. The native core executes bounded DC (linear, piecewise-linear diode, or explicitly parameterized Shockley diode models), linear R/L/C AC, and fixed-step RC/RLC transient calculations for explicit idealized netlists; these calculations do not validate the saved graph unless an explicit graph-bound mapping route is used, and they do not constitute nonlinear/SPICE equivalence or hardware validation. Poppler `pdftotext` availability is also optional and no real datasheet extraction was run. Deck filtering is a guardrail, not proof of parser safety. Firmware compilation, PCB design, hardware testing, and manufacturing checks are not implemented. KiCad DRC now runs only on an explicitly imported board when `kicad-cli` is installed; no real DRC was performed in this environment. A DRC summary is evidence only for that tool run, not electrical or manufacturing approval. Validation artifacts distinguish these states; do not interpret a graph pass or netlist file as electrical approval.

The clock benchmark intentionally reports that the sample inventory is insufficient for the discrete six-digit design (including only three CD4511 display drivers) and does not invent pin wiring. Intake-time calculation examples are illustrative. The LED-resistor workflow uses manually entered quantities, is not extracted from the circuit graph, and is not design approval. RC transient and DC MNA mappings are user-authored rather than inferred; event-driven/sequential timing simulation, mixed-signal co-simulation, and automatic model-to-simulator conversion remain unimplemented. The digital waveform route is only sample-driven ideal Boolean logic with edge-triggered DFF state.

## Architecture

- `core/`: C++20 typed circuit/element model, bounded MNA and RC transient solver, C ABI v1, standalone CLI, and native CTest suite.
- `circuitmind/`: Python standard-library server, typed graph/workflows, unit validation, ctypes bridge, native solver adapters, KiCad adapters, persistence/snapshots.
- `web/`: browser-based local project intake, circuit-model editor, and bounded RC synthesis workflow.
- `tests/`: Python/API/native-ABI regression tests. Python/native tests compile the C++ shared library to a temporary directory; native CMake tests run separately via CTest. No actual KiCad/ngspice run is claimed.
- `docs/DEVELOPMENT_PLAN.md`: capability inventory and release criteria (not a phased delivery plan).
- `docs/CIRCUIT_ENGINE_ARCHITECTURE.md`: versioned subsystem contracts, C++/Python boundary, current RC synthesis workflow, and remaining platform scope.
- `docs/CIRCUIT_ENGINE_PROGRESS.md`: current implementation status, verified checks, and remaining limitations.

Projects live below `CIRCUITMIND_DATA_DIR/projects/<project-id>/`. Tool availability probes report installation/version only; they do not imply a validation operation ran.
